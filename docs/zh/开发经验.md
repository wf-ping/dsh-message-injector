## 1. 一句话总结

> dsh 插件 = **一个前后端小应用**：后端跑在 dsh 服务进程里（配置、校验、存储），
> 前端跑在浏览器里（按钮、表单、自动注入）；前端代码必须**预先打包成纯 JS**；
> 用 `dsh plugin add` 官方命令安装后，插件声明 `dsh.bundle` 才会被真正"挂载"生效。
> 本项目最大的认知收获：**技能是会话级激活的，一个会话只需注入一次**——这推翻了最初的
> "技能预设自动填充"定位，最终做成"每条消息注入任意内容"的 `dsh-message-injector`。

## 2. dsh 插件到底是什么（零基础篇）

### 2.1 插件 = 前端 + 后端两半

dsh 官方把插件分成两半，叫 **host half / client half**（宿主半区/客户端半区），
本质就是传统意义上的**后端 / 前端**：

| | 跑在哪里 | 干什么 | 对应本项目的文件 |
|---|---|---|---|
| **后端**（host half） | dsh 的服务端进程（你电脑上跑的 dsh） | 配置格式定义、保存校验、数据持久化 | `src/index.ts` → 构建成 `lib/index.js` |
| **前端**（client half） | 你的浏览器 | 按钮、表单、自动注入逻辑 | `src/client.tsx` → 构建成 `lib/client.js` |

> **Q：为什么要分两半？**
> 因为你要的"预设按钮"是画在网页上的（浏览器代码），但配置要存到 dsh 的服务端
> （服务端代码）。两者通过 dsh 的框架互相配合——前端通过官方接口读写后端的配置。
>
> **Q：前端/后端各有一个"产物文件"，lib/index.js 和 lib/client.js 怎么区分？**
> 看 package.json 的 `exports` 表：
> - `"."` → `lib/index.js` → **后端**（谁 import 这个包谁拿到它，dsh 服务端加载插件用它）
> - `"./client"` → `lib/client.js` → **前端**（dsh 找浏览器代码就认这个约定子路径）
>
> "index" 是 npm 包的默认入口名的通用惯例；"client" 是 dsh 生态找前端代码的固定暗号。

### 2.2 为什么前端代码必须"预先打包"？

**dsh 的浏览器不认 TypeScript，只认纯 JS。** 你写的 `src/client.tsx` 是 TS+JSX（人写的、
带类型、带 JSX 标签），浏览器读不懂。所以要用 esbuild 把它"翻译"成纯 JS 文件
（`lib/client.js`），dsh 的浏览器才能执行。

这个"翻译"动作就是 `pnpm build`（跑 `scripts/build.mjs`，内部调 esbuild）。

> **Q：为什么不用 `npm build`？**
> 本项目用 pnpm 管理依赖（安装命令都是 `pnpm xxx`）。`pnpm build` 只是运行
> package.json 里 `scripts.build` 定义的那条命令（`node scripts/build.mjs`），
> 叫 `pnpm run build` 也行。换 npm 也能跑同样的脚本，只是本项目统一用 pnpm。
>
> **Q：构建产物为什么提交进仓库？**
> 这样别人（或未来的你）克隆仓库后**直接就能安装**，不需要先装构建工具链。
> 只有**改动过 `src/` 里的代码**才需要重新 `pnpm build`。
>
> **Q：删了 lib/ 目录怎么恢复？**
> 只删 lib/ → 跑 `pnpm build`；连 node_modules 一起删了 → 先 `pnpm install` 再 `pnpm build`
> （build 需要 esbuild，它装在 node_modules 里）。

### 2.3 插件怎么被 dsh"发现并挂载"？

一个插件包要被 dsh 真正用起来，需要三个声明齐活（都在 `package.json` / 仓库文件里）：

1. **`dsh.bundle.patch`**：告诉 dsh"我是正式插件，安装时请把我挂载为 profile 层"。
   它指向仓库里的 `bundle.patch.yml`（一行"加载指令"：`- insert: {id, name: 包名}`）。
   > **这是本项目踩的最大坑**：没声明它时，`dsh plugin add` 只把插件当"普通依赖"
   > 装进目录，**永远不会生效**——症状是"装了，页面毫无变化"。
2. **`exports["./client"]`**：告诉 dsh"我的前端代码在哪"（`lib/client.js`）。
3. **入口**（`main`/`exports["."]` → `lib/index.js`）：dsh 服务端加载插件时执行它，
   里面的 `apply(ctx)` 就是插件的"启动函数"——注册配置、注册 UI、启动轮询都在这里。

> **Q：`apply(ctx)` 是什么？**
> 每个 dsh 插件都导出一个 `apply(ctx)` 函数。dsh 加载插件时调用它，把上下文对象 `ctx`
> 交给你——你通过 `ctx` 注册各种能力（配置命名空间、UI 槽位、定时器等）。
> 插件卸载时，通过 `ctx` 注册的东西**自动清理**，不用手动收拾。

### 2.4 官方安装路径（只用这一种）

```bash
dsh plugin --profile web add <仓库路径>        # 从本地目录装（软链接）
dsh plugin --profile web add github:用户/仓库  # 从 GitHub 装（克隆副本）
dsh plugin --profile web remove dsh-message-injector   # 卸载
```

- **本地路径安装**：装的是**软链接**，指向你的仓库——改代码后 `pnpm build` + 重启 dsh
  即生效，不用重装。
- **GitHub 安装**：装的是**克隆副本**，与本地代码无关——更新要重新 `add` 拉取。

> **Q：为什么不用 dsh 官方教程里的 `--patch` 本地加载方式？**
> 它需要一个 `cordis.yml` 配置文件，里面要写**项目绝对路径**（如 `/Users/你的名字/...`）。
> 项目要开源的话，这会把你的个人信息泄露出去。所以我们放弃它，统一走官方安装命令。

## 3. 本项目的定位演变（为什么最后做成这样）

### 3.1 最初的设想

最初叫 `dsh-skill-injector`：预设常用技能组合（如 `/grill-me`），每次对话前自动填充到输入框，
省去手动输入。当时的需求讨论（/grill-with-docs 逐项确认）包括：填充到输入框首行、
选中即持续生效、反选停止、全局持久化、数据模型（组名/描述/技能列表/启用）、
校验规则、样式与 FULL ACCESS 按钮一致等。

### 3.2 一个事实推翻了定位

开发过程中发现一个**关键事实**：dsh 的技能是**会话级激活**的——一条消息里触发 `/grill-me`
后，**整个会话**都持续生效，后续消息根本不需要再带。而插件当时的设计是"每条消息都自动填充"，
导致**每条消息都把技能全文重复注入**一次（dsh 对重复注入没有去重）——token 消耗像滚雪球。

由此推理出：

- **"每个会话填充一次"** = 手动输入一次就行（五个字的事），**不值得插件化**；
- **"每条消息注入固定内容"** 才是真实需求——有些人确实需要每条消息都带指令前缀、
  格式要求等固定内容。

### 3.3 最终定位

更名 **`dsh-message-injector`**（消息注入器）：

- 内容泛化为**任意文本**：普通文本（如"请用中文回答"）原样注入；
  以 `/` 开头的行视为**技能调用**（如 `/grill-me`），保留存在性校验（缺失警告、注入时跳过）。
- 行为：选中预设组后，**每条消息**自动把内容注入输入框首行（空输入框才注入，绝不打扰已有内容）。
- 附带价值：这是一次**练手性质**的插件开发——完整走通 dsh 插件从需求到上线的全流程。

> **Q：既然"每条消息注入"会浪费 token（技能重复注入），为什么还要这个功能？**
> 对**普通文本**（指令前缀、格式要求）不存在重复注入问题——文本就是文本，每条消息带一遍
> 是用户明确想要的。只有**技能调用**行才会因为重复而浪费 token，所以文档里建议：
> 不需要"每条消息都带技能"时反选停止，或期待"仅首条注入模式"（已列入畅想清单）。

## 4. 踩坑全记录（症状 → 根因 → 修复）

> 按时间顺序，记录本项目真实踩过的每个坑。每条都是"症状 → 根因 → 修复"三段式。

### 坑 1：研究阶段过度投入，烧掉大量 token

- **症状**：为了搞清 dsh 插件机制，派了 3 个深挖源码的子代理，消耗 30M+ token，用户肉痛。
- **根因**：没有先建立"最小回路"，一上来就全面深挖所有机制。
- **修复/教训**：应该**先做最小可加载验证**（hello world 插件跑通），再按需深入。
  研究要克制：优先读官方现成例子（如 dsh-vscode-bridge），别全局扫源码。

### 坑 2：前端半区必须预构建（浏览器无 TS 编译）

- **症状**：最初以为 cordis.yml 指向 `src/index.ts` 就能让浏览器加载 TS。
- **根因**：dsh 浏览器端的加载器用 `new Function` 执行客户端代码，**明确不支持 TS/JSX**；
  前端半区必须是预构建的纯 JS bundle（`window.__ModuleLoader__.load({id, factory})` 形态）。
- **修复**：esbuild 把 `src/client.tsx` 打包成 `lib/client.js`，包一层
  `__ModuleLoader__.load` 包装（factory 里 `require` 外部模块由浏览器运行时提供）。
  顺带：**JSX 必须写在 `.tsx` 文件**里（`.ts` 不解析 JSX，会报语法错）。

### 坑 3：cordis.yml 的 insert name 指向 .ts 文件 → 客户端半区发现失败

- **症状**：宿主半区加载成功，但前端 UI 永远不出现。
- **根因**：dsh 找"这个插件的浏览器代码在哪"时，用
  `require.resolve('<name>/package.json')` 探测——name 指向 `.ts` 文件就探测失败，
  判定"没有客户端半区"。
- **修复**：insert 的 name 必须指向**仓库根目录**（含 package.json 的目录）。

### 坑 4：cordis.yml 含绝对路径，不适合开源

- **症状/隐患**：cordis.yml 里必须写 `/Users/你的名字/...` 绝对路径，开源即泄露个人信息。
- **根因**：`--patch` 本地加载方式天生需要绝对路径。
- **修复**：**放弃 --patch**，只走官方 `dsh plugin add/remove`；仓库里不维护 cordis.yml。
  安装时路径只记在你的 `$DSH_HOME`（本机配置），不进仓库。

### 坑 5：缺 `dsh.bundle` 声明 → 装了但永远不生效

- **症状**：`dsh plugin add` 显示成功（"Done"），页面毫无变化。
- **根因**：安装输出里那句警告就是答案——`dsh-skill-injector declares no dsh.bundle —
  installed as a plain dependency, not a profile layer`（只被当普通依赖装了，没挂载）。
  顺带查清了机制：`dsh plugin add` 只把**声明了 `dsh.bundle`** 的包加入 profile 的
  bundles 列表，启动时才会加载。
- **修复**：package.json 加 `"dsh": { "bundle": { "patch": "./bundle.patch.yml" } }`，
  并创建 `bundle.patch.yml`（内容：`- insert: {id, name: 包名}`，只用包名，无绝对路径）。
  重新 add 后，bundles 列表出现插件名 → 重启生效。

### 坑 6：`ctx.logger` 是服务工厂，直接 `.info` 静默无效

- **症状**：写了 `ctx.logger?.info('loaded')`，终端永远不打印。
- **根因**：cordis 4.x 的 `ctx.logger` 是一个**服务工厂**，要 `ctx.logger('名字')`
  才能拿到 logger 实例；`ctx.logger?.info` 是 undefined，静默无效。
- **修复**：改用 `console.log`（终端必定可见）。

### 坑 7：useSyncExternalStore 传裸方法 → 丢失 this → 渲染崩溃

- **症状**：插件两个 UI 都不渲染，控制台报
  `TypeError: Cannot read properties of undefined (reading 'store')`。
- **根因**：`useSyncExternalStore(scope.subscribe, scope.getSnapshot)` 把
  `scope.getSnapshot` 当**裸函数**传给 React，React 调用时没有 `this` 上下文，
  方法内部 `this.store` 就是 undefined。settings scope 的方法依赖 `this`。
- **修复**：用箭头函数包裹：
  `useSyncExternalStore((cb) => scope.subscribe(cb), () => scope.getSnapshot())`。

### 坑 8：每条消息重复注入技能 → token 滚雪球（定位转折点）

- **症状**：会话里每条消息都带 `/grill-me`，token 消耗异常快。
- **根因**：技能全文注入路径**没有去重**（源码核实：skill 工具每次调用都全量渲染内容），
  而技能是**会话级激活**的——重复带 = 每轮请求都多一份完整技能全文。
- **修复（定位层面）**：重新思考产品形态 → 更名 `dsh-message-injector`，
  "每条消息注入任意内容"成为新定位；"仅首条注入模式"列入畅想。
  （注：对普通文本不存在此问题，只有技能调用行会因重复而浪费。）

### 坑 9：git 事故三连

- **症状 1**：`git add -A` 把 pnpm 的本地缓存目录 `.pnpm-store`（33MB）提交了。
  - 根因：pnpm 在项目内建了内容寻址缓存（纯缓存，无需入库）。
  - 修复：加入 `.gitignore`，并 `git rm --cached` + 修正提交历史。
- **症状 2**：`git commit --amend` 后，部分文件从提交里"消失"（index 状态混乱）。
  - 根因：amend 用的是当时 index 的状态，中间有人 reset 过，状态没对上。
  - 修复：`git reset --soft <旧提交>` 把暂存内容找回来，重新一次性提交。
- **症状 3**：用户 `git reset --soft HEAD^` 回退多层后，怀疑内容丢失。
  - 结论：**soft reset 不动工作区文件**，内容全在，重新提交即可；reflog 里可找回一切。

### 坑 10：开源前的隐私审计

- **症状/隐患**：
  - 仓库里出现过某个开发者的绝对路径（形如 `/Users/某用户名/...`，cordis.yml，已删）；
  - git 提交作者是**真实姓名 + 邮箱**；
  - 旧提交对象里残留真实身份。
- **修复**：
  - 全库扫描绝对路径/用户名/邮箱/IP，清除；
  - git 作者改为匿名身份（GitHub noreply 邮箱，形如 `用户名@users.noreply.github.com`）；
  - `git reflog expire --expire=now --all && git gc --prune=now` 物理清除含真实身份的旧对象；
  - 验证：`git log --format='%an <%ae>'` 全为匿名；`git fsck --unreachable` 无残留。
  - 顺带发现：pnpm-lock.yaml 不含任何 URL（比 npm 锁文件更隐私友好）。

### 坑 11：文档组织反复迭代

- 症状：README 越写越长、前后端术语（半区）让人困惑、位置描述（FULL ACCESS 按钮旁）
  对用户不友好、中英文混排。
- 修复：
  - README 精简为门面页，细节拆分到 docs/zh + docs/en（语言目录 + 对应语言文件名）；
  - 术语统一"前端/后端"（dsh 官方"半区"仅对照时提及）；
  - 位置描述改为"输入框左下角"（用户可感知），技术文档才谈槽位；
  - 语言切换链接放文档开头，中文 README 只链中文文档。

## 5. 下次开发少走弯路的流程建议

按顺序执行，每一步都有明确产出：

1. **先搞清核心机制，再定产品形态**
   本项目最大的教训：技能"会话级激活"这个事实，直接推翻了最初的产品定位。
   动手前先确认"这个功能在 dsh 里到底是怎样生效的"——一个事实可能改变整个设计。

2. **先做最小回路验证，再深入功能**
   第一步先让"hello world 插件"在官方路径下加载成功（终端看到日志），
   证明：包结构、声明、安装、加载全链路通。之后每加一个功能都小步验证。
   研究要克制：优先读官方现成插件（dsh-vscode-bridge）当模板，别全局深挖源码。

3. **三份声明齐活再装**
   `dsh.bundle.patch` + `exports["./client"]` + 入口文件，缺一个都"装了不生效"。
   装完检查：profile 的 bundles 列表里有插件名吗？（有 = 挂载了）

4. **测试只走官方路径，由用户亲自执行**
   开发环境跑 `dsh web` 可能和现有实例抢端口（3080 被占用），用 `--port 3090` 起测试实例。
   不自启动 dsh 做自动化验证；安装/卸载/验收由用户亲自来。

5. **改动小步提交，历史可回退**
   别用 `git add -A` 一把梭（会误提交 .pnpm-store 之类）；
   提交前 `git status` 检查；amend 前先确认 index 状态；用 soft reset 找回内容。

6. **产物提交，保证"即装即用"**
   `lib/` 构建产物提交进仓库——别人克隆后直接 `dsh plugin add` 就能用，不用装工具链。

7. **文档与代码同步，一次改名全库同步**
   改名/改定位时，用 `grep -rn "旧名|旧术语"` 全库扫描，逐个甄别，
   别只改代码不改注释和配置文件。

8. **开源前做隐私审计**
   扫描绝对路径/用户名/邮箱/IP；git 作者匿名化（noreply 邮箱）；`gc` 清除旧对象；
   全历史检查（`git log -p` 含被删行）。提交信息也别带个人信息。

## 6. 常见疑问速查（FAQ）

**Q1：这个插件到底怎么工作的？**
选中一个预设组 → 插件每 500ms 看一眼输入框 → 发现输入框是空的 →
把组里的内容行（空格连接成一行）填进输入框首行 → 你发送 → 输入框清空 →
下一轮轮询再填。输入框有内容时不填（保护你的草稿）。反选就停止。

**Q2：为什么要用 500ms 轮询，不用"输入框变化事件"？**
轮询简单可靠：每 500ms 看一眼状态，逻辑直接、没有时序坑。500ms 的感知延迟用户无感。
（需求讨论时用户拍板选的轮询方案。）

**Q3：`setDraft` 是什么？为什么不能直接改输入框的值？**
dsh 的输入框是 React 受控组件——直接改 DOM 的值不会同步到 React 状态，发送时会发空。
所以必须走官方通道 `input.setDraft(text)`（一次事务，可撤销）。

**Q4：settings 命名空间是什么？**
就是"这个插件存在 dsh 配置里的一个抽屉"，名字叫 `message-injector`。
预设组列表、当前选中组都存在这里（`$DSH_HOME/settings.yaml`），
跨会话、跨刷新、跨标签页保持。

**Q5：为什么改代码后要重启 dsh？刷新浏览器行不行？**
- 改**后端**（lib/index.js）：必须重启——模块在 dsh 进程启动时已读进内存，改文件不会重载。
- 只改**前端**（lib/client.js）：刷新浏览器即可（服务器每次按路径实时读文件）。
- 不确定/都改了：重启最稳妥。文档统一写"重启"是保守的一条规则。

**Q6：本地安装和 GitHub 安装有什么区别？**
本地路径装的是**软链接**（指向你的仓库，改代码即生效）；GitHub 装的是**克隆副本**
（与本地代码无关，更新要重新 add）。详见 docs/zh/安装.md。

**Q7：为什么"每条消息注入技能"会浪费 token？**
技能是会话级激活的，注入一次整个会话生效；但 dsh 对重复注入**没有去重**——
每条消息再带一次 `/grill-me`，就会把技能全文**再注入一份**，且永远留在上下文里。
所以普通文本随便带，技能调用行别重复带（不需要就反选，或等"仅首条注入"功能）。

**Q8：为什么项目里没有 cordis.yml？**
`--patch` 本地加载才需要它，且它要写绝对路径（泄露隐私）。我们统一走官方安装。

**Q9：包名变了（skill-injector → message-injector），旧安装怎么办？**
`dsh plugin remove <旧包名>` 再 `dsh plugin add <新仓库>`；
旧配置（旧命名空间）作废，需要重新建预设组。

**Q10：这些经验对"下次开发"有什么用？**
最值钱的几条：先确认核心机制再定产品、先跑通最小回路、三份声明缺一不可、
测试走官方路径、产物提交、开源前隐私审计——每一条都对应本项目真实踩过的坑。
