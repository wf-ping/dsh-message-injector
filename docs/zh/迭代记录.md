# 迭代记录

> 按时间线记录迭代过程与决策背景。**CHANGELOG.md 是结果清单，本文档是过程记录**——为什么这么做、踩了什么坑、怎么拍板的。

## 2026-10-28（续 2）— 配置搬回宿主：终端与 VS Code 面板共享

- **现象**：终端 `dsh web` 和 VS Code 面板（`fengze233.dsh-vscode-panel`）各有一份预设，互不可见。
- **根因**：localStorage 按 origin 隔离。VS Code 面板把 DSH 页面装进 `vscode-webview://<uuid>` 的 service worker 里（扩展 `out/extension.js` 注释自述 origin 会被重写），与 `http://127.0.0.1:3080` 不是同一个存储桶；扩展端口被占时临时换端口（`msg.portFallback`）又会再切一桶。
- **决定**：配置搬回 dsh 配置系统——设置命名空间 = profile 条目 id `dsh-message-injector`，落盘 `cordis.patch.yml`，两个入口读同一份。宿主 `Config` 里 `groups` / `selected` 都标 `.volatile()`（settings 只投影 volatile 字段），前端走 `ctx.inject(['configForms'])` → `configForms.get(entryId)`。
- **迁移**：localStorage 降级为兜底 + 迁移源。首次接管宿主时把旧数据并进去：同名组以宿主为准，旧数据独有的组补进去；成功后写 `dsh-message-injector:migrated-v1` 标记。迁移完成前不镜像，否则镜像会先冲掉待迁移的源数据。
- **稳定性设计**：`utils/store.ts` 对外是稳定表单（后端可替换），组件与注入服务继续用同一个 `scope`；宿主没服务该命名空间时快照为 `unavailable`，继续走 localStorage。

## 2026-10-28 — 适配 dsh 0.2 配置系统重写

- **现象**：dsh 升级到 0.2.1-rc.2 后插件失效——设置里找不到配置卡。
- **根因**（读 0.2.1-rc.2 安装包源码确认，非猜测）：
  - `@deepseek-ai/dsh-settings` 不再导出 `installSettingsSection` / `settingsNamespace`，后端 import 直接拿不到函数；
  - 客户端服务 `settingsScope` 已删除，入口 `inject` 里仍写着它 → 插件永远等不到依赖，永不加载；
  - 槽位 `settings.plugin.item` 已删除，配置页搬进新的插件管理页。
- **新模型**：配置 schema 即表单——`describe()` 读每个 loader 条目的 `Config`，命名空间 = **条目 id**（不是插件自选命名空间）；只有标了 `.volatile()` 的字段可写；写入落到当前 profile 的补丁层（`cordis.patch.yml`），不再是 `settings.yaml`。
- **落点**：`plugins.row.config`（keyed 槽，key = `<包名>#<行 id>`），渲染在侧边栏「插件」→ 本插件 → 行「配置」；官方契约写明「插件自己的配置属于 `plugins.bundle.config` / `plugins.row.config`，`plugins.item` 留给官方设置页」。
- **配套**：`ctx.settings.configure({ auto: false })` 关掉自动生成页；`ctx.configForms.whileServed([entry], …)` 让宿主没服务该命名空间时不出现残留；读用 `ctx.configForms.get(entry)`，写用 `mutate([{op:'set', path:[field], value}])`；F6-6 自动反选改为订阅表单快照。
- **直达入口**：旧的 aria + 文案 DOM 定位不再管用（设置面板里已无本卡），改用插件管理页的反射服务 `pluginNavigation.openBundle(包名)`。
- **数据迁移**：旧 `settings.yaml` 已被 dsh 重命名为 `settings.yaml.imported`，`message-injector:` 段不会再被读取；升级后需在界面重新录入（README 已写明）。

## 2026-10-28（续）— 转纯前端：配置存 localStorage

- **背景**：适配 0.2 时一路跟到 dsh 新配置系统（`Config.volatile` + `ctx.configForms` + `plugins.row.config`），跑通后又遇到两处硬伤：一是宿主侧写入偶发「宿主拒绝了这次写入」，二是插件页行配置的入口太深（插件页 → 包 → 行 → 配置）。
- **决定**：预设组是纯界面偏好，不该占用 dsh 的配置系统。改成浏览器 localStorage（键 `dsh-message-injector:config`）+ 自带弹窗（原生 `<dialog>`）。
- **换来的好处**：写入即时、不会冲突、无宿主依赖；宿主端只剩加载入口，连 `schemastery` 依赖都省了。
- **代价**：换浏览器/清站点数据会丢配置；跨设备不同步。对这类"输入前缀偏好"可接受。
- **顺带的行为决策**：一次「选中 + 会话」只自动填一次；手动删空 → 立即取消选中（订阅输入状态，不等轮询）；发消息后重新武装。用户原话："我手动删空的时候，就不要无脑填充了"。

## 2026-08-30 — 从零到开源（一次完整迭代）

### 阶段 1：需求讨论与定位（/grill-with-docs 逐项确认）

- 最初设想「技能预设自动填充」（`dsh-skill-injector`）：预设常用技能组合，自动填入输入框。
- **一个事实推翻定位**：dsh 技能是**会话级激活**的——一个会话只需注入一次，手动输入即可；而"每条消息注入固定内容"才是真实需求。更名 `dsh-message-injector`，内容泛化为任意文本（`/` 开头行视为技能调用，保留存在性校验）。
- 术语表（CONTEXT.md）、需求文档（需求.md）在此阶段成型。

### 阶段 2：骨架与最小回路

- 双半区结构 + 三声明（`dsh.bundle` / `exports["./client"]` / 入口）齐活。
- 踩坑实录（详见 开发经验.md）：
  - 缺 `dsh.bundle` → 装了不生效；
  - `useSyncExternalStore` 裸方法丢 `this` → 渲染崩溃；
  - `ctx.logger` 是服务工厂 → `.info` 静默无效。

### 阶段 3：文档体系

- README 精简为门面页，细节拆分 `docs/zh` + `docs/en`；术语统一"前端/后端"；位置描述改为用户可感知的"输入框左下角"。

### 阶段 4：配置卡 UI 对齐官方

- 手写样式配置卡与官方卡（WebSearch/Bash/AgentLoop）格格不入 → 照抄官方视觉参数（radius 12 / border l2 / bg layer-3 / input 34px），全走 `--dsw-alias-*` 令牌 + 自有类名（**禁止引用 dsh 内部哈希类名**）。
- 抽象通用组件 `ConfigCard`（折叠标题栏 + 表单体 + 放弃/保存脚注 + 展开信号）。
- 交互打磨：组折叠（默认收起）、新增组压栈首位、添加后自动滚动露出。

### 阶段 5：设置直达

- 需求：选择器菜单底部「设置」→ 一键打开设置面板并展开配置卡。
- 事实：dsh 无公共 API（SettingsRoot 的 open/分区均为内部 state）→ 采用官方 aria 属性（`button[aria-haspopup="dialog"]`）+ 官方导航文案（`插件`/`Plugins`）定位，配置卡展开用**一次性信号**（挂起/消费/订阅），任一步失败优雅降级。

### 阶段 6：结构重构

- `src/` 按官方 half 分法分 `host/`（后端）/ `client/`（前端），领域类型抽 `shared/types.ts`。
- 前端按职责分层：`types/`（契约类型）`api/`（数据访问）`services/`（业务服务）`logic/`（纯逻辑）`locales/`（词典）`utils/`（通用工具）`components/`（UI 组件），入口 `index.tsx` 只做接线。
- 滚动控制/一次性信号/CSS 注入/设置定位/技能目录抽象为通用模块。
- 自带 skill（`.agents/dsh-plugin-dev`）与模板同构重构。

### 阶段 7：开源准备

- **安全审计**：全部提交历史 + 不可达对象扫描（密钥/绝对路径/邮箱/IP 零命中），真实身份匿名化（noreply 邮箱）、31 个不可达对象物理清除（`reflog expire` + `gc --prune=now`）。
- 新增 LICENSE（MIT）、npm `keywords`（dsh-plugin 等，GitHub topic 需推送后在仓库页设置）。
- README 说明配置存储位置（`$DSH_HOME/settings.yaml`）；使用说明补「使用建议」（长文本整理为 SKILL）与「典型使用流程」。

## 后续迭代约定

1. 每个功能/修复：更新 CHANGELOG（对应版本条目）
2. 语义化版本 bump（package.json + CHANGELOG 日期）
3. 打 tag（`vX.Y.Z`）+ 推送
4. GitHub Release（内容 = CHANGELOG 该版本条目）；用户可用 `dsh plugin add github:wf-ping/dsh-message-injector#vX.Y.Z` 固定版本安装
